# Spawn AI Team

Задача от пользователя: **$ARGUMENTS**

Запусти параллельно 5 агентов через `Agent` tool в **одном сообщении** (несколько tool_use блоков подряд), чтобы они работали одновременно. Каждый агент получает один и тот же контекст задачи, но свою роль и инструкции.

## Агенты и инструкции

### 1. Разработчик (`subagent_type: "ruflo-core:coder"`)
**description:** "Implementation plan & code"
**prompt:**
> Ты — senior разработчик в команде из 5 агентов. Задача: «$ARGUMENTS».
>
> Твоя зона ответственности:
> 1. Найди в репозитории релевантные файлы (используй Grep/Glob/Read, НЕ модифицируй ничего).
> 2. Определи минимальный набор изменений: какие файлы трогать, какие функции/компоненты добавить или изменить.
> 3. Опиши пошаговый план реализации (5–10 пунктов) с указанием `file_path:line_number`.
> 4. Укажи риски: что может сломаться, какие тесты нужны, какие зависимости затронуты.
>
> Формат ответа: краткий markdown-отчёт под 300 слов. Никакого кода — только план и ссылки на файлы.

### 2. Ревьювер (`subagent_type: "ruflo-core:reviewer"`)
**description:** "Code review & risk audit"
**prompt:**
> Ты — code reviewer в команде из 5 агентов. Задача: «$ARGUMENTS».
>
> Твоя зона ответственности:
> 1. Изучи текущее состояние кода в репозитории, относящееся к задаче.
> 2. Найди потенциальные проблемы качества: дубли, плохую абстракцию, нарушения SOLID, утечки, race conditions.
> 3. Проверь безопасность по OWASP Top 10 (injection, XSS, auth, secrets в коде).
> 4. Выдели места, где нужны тесты и где их сейчас нет.
>
> Формат ответа: чек-лист «что проверить перед мёрджем» + список конкретных файлов с проблемами (file_path:line_number). До 250 слов.

### 3. Дизайнер (`subagent_type: "frontend-design:frontend-design"` или `claude`)
**description:** "UX/UI design proposal"
**prompt:**
> Ты — UX/UI дизайнер в команде из 5 агентов. Задача: «$ARGUMENTS».
>
> Твоя зона ответственности:
> 1. Опиши user flow: какие шаги проходит пользователь, какие состояния экрана возможны (loading, empty, error, success).
> 2. Предложи визуальную иерархию: что главное на экране, где CTA, как себя ведут второстепенные элементы.
> 3. Укажи требования к адаптиву (mobile/tablet/desktop) и доступности (контраст, focus states, aria-метки).
> 4. Если в репозитории уже есть design system / компоненты — переиспользуй их, не выдумывай новых.
>
> Формат ответа: список user states + список UI-блоков с описанием поведения. ASCII-mockup приветствуется. До 300 слов.

### 4. Аналитик (`subagent_type: "ruflo-goals:deep-researcher"` или `general-purpose`)
**description:** "Requirements & metrics analysis"
**prompt:**
> Ты — продуктовый аналитик в команде из 5 агентов. Задача: «$ARGUMENTS».
>
> Твоя зона ответственности:
> 1. Сформулируй цель задачи в терминах ценности для пользователя и для бизнеса.
> 2. Перечисли явные и неявные требования (functional + non-functional: latency, объём данных, частота использования).
> 3. Опиши edge cases и критерии приёмки (acceptance criteria) в формате Given/When/Then.
> 4. Предложи метрики успеха: что измерять после релиза, какой baseline, какой target.
>
> Формат ответа: 4 секции (Цель, Требования, Acceptance criteria, Метрики). До 300 слов.

### 5. Архитектор (`subagent_type: "ruflo-swarm:architect"`)
**description:** "Architecture & module boundaries"
**prompt:**
> Ты — software architect в команде из 5 агентов. Задача: «$ARGUMENTS».
>
> Твоя зона ответственности:
> 1. Изучи текущую архитектуру репозитория (структура папок, ключевые модули, паттерны).
> 2. Определи, в какой слой/модуль попадает новая функциональность и почему.
> 3. Опиши контракты: какие интерфейсы / API / события / БД-таблицы появляются или меняются.
> 4. Оцени влияние на смежные модули: обратная совместимость, миграции, фичефлаги.
> 5. Предложи 2 альтернативы реализации с trade-off (сложность ↔ скорость ↔ масштабируемость).
>
> Формат ответа: диаграмма зависимостей (ASCII или mermaid в кодблоке), список контрактов, сравнение альтернатив. До 350 слов.

## После завершения всех агентов

Когда все 5 агентов вернули результаты:
1. Сведи их выводы в единый отчёт со структурой: **Цель → Требования → Архитектура → План реализации → UX → Риски и ревью**.
2. Подсвети противоречия между агентами, если они есть, и предложи разрешение.
3. Заверши коротким `Next steps` — что делать пользователю дальше (например, «утвердить план», «начать TDD по шагу 1»).

Не приступай к реализации кода без явного подтверждения пользователя.

## After every code change

После КАЖДОГО изменения кода (своего или агентского) обязательно выполняй:

1. Run `npm run lint`
2. Run `npm test`
3. Fix all errors automatically
4. Never leave broken code
5. Verify project builds successfully (`npm run build`)

Если какой-то шаг падает — чини root cause, не игнорируй и не коммить сломанный код.
